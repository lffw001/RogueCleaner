# 全局厂商识别与误报治理设计

## 目标

彻底替换“把所有字段拼成字符串后做任意子串匹配”的厂商识别方式，避免 GUID、哈希、注册表路径、命令参数或普通单词偶然包含厂商短词时产生误报。修复必须覆盖右键菜单、资源管理器入口、启动项、启动文件夹、服务、计划任务、浏览器宿主、文件关联、运行进程和卸载项全部扫描入口。

本次只使用本地证据，不上传文件、哈希或用户环境信息，不接入在线信誉服务。

## 核心原则

1. **厂商身份与异常行为分离**：先判断对象属于谁，再判断它做了什么；签名合法不代表行为安全，行为可疑也不能反推出厂商。
2. **结构化字段取代混拼文本**：显示名、Publisher、文件路径、命令参数、GUID、注册表位置分别保存和判断。
3. **不透明标识不参与品牌匹配**：GUID、哈希、PID、版本号、完整注册表路径、随机文件名和系统宿主参数不得用于厂商关键词匹配。
4. **强证据优先，弱证据不能单独定性**：只有可信来源达到门槛才显示具体厂商并进入对应处理链。
5. **冲突时保守**：两个强证据指向不同厂商时，不归类、不允许清理，并在证据中记录冲突原因。

## 结构

### VendorEvidence

每个扫描入口构造统一的结构化证据对象，包含：

- 人类可读字段：显示名、Publisher、描述、产品名。
- 执行字段：原始命令、解析后的 EXE/DLL、快捷方式目标、COM Server、服务 ImagePath、计划任务 Action Path。
- 安装字段：安装目录、DisplayIcon、MSI ProductCode、MSI 产品名和发布者。
- 技术字段：注册表位置、GUID、PID、原始参数；仅用于报告，不参与普通厂商匹配。
- 行为字段：入口类型、是否开机启动、是否计划拉起、是否浏览器宿主、是否隐藏、是否缺少卸载入口、是否命中明确弹窗/守护组件。

### VendorIdentityResolver

统一身份解析器按以下顺序补全证据：

1. 解析当前入口能指向的真实厂商文件。
2. 读取 `FileVersionInfo.CompanyName`、`ProductName`、`FileDescription`。
3. 使用 Windows 信任接口验证 Authenticode 完整性，再读取签名主体。
4. 对 MSI ProductCode 调用 Windows Installer API，获取产品名、Publisher、安装目录和本地缓存包；绝不把 `msiexec.exe` 的微软签名当成产品厂商。
5. 将文件路径与已安装软件的 `InstallLocation`、DisplayIcon 和 Publisher 建立归属关联。
6. 使用规范化厂商别名和明确技术标识做最终匹配。

文件元数据、签名和 MSI 查询结果按规范化路径或 ProductCode 缓存，避免同一扫描反复验签。

### VendorIdentityResult

返回：厂商、置信度、命中的证据来源、冲突说明和是否允许进入清理链。报告保留可读证据，但不暴露无关本机数据。

## 证据等级

| 等级 | 证据 | 用途 |
|---|---|---|
| 强 | 有效 Authenticode 签名主体、有效签名 MSI 的签名主体 | 可独立确认厂商身份 |
| 中 | Publisher、MSI Publisher、文件 CompanyName、明确产品名、安装目录归属、厂商特有 EXE/DLL/服务名/组件名 | 两项相互独立的中证据组合后确认；单项只作候选身份 |
| 弱 | 普通显示文字、描述中的宽泛品牌词 | 只加辅助分，不独立确认 |
| 禁止 | GUID、哈希、PID、版本号、完整注册表路径、系统宿主及其参数 | 仅展示，不参与身份判断 |

厂商规则中的短词必须改为明确别名或有边界的词元。`2345`、`360` 等纯数字品牌只有在人类可读字段中作为完整词元，或出现在 `2345Explorer`、`360Safe` 等明确技术标识中才有效。`KAV`、`TBS`、`XMP`、`SGTool` 等低熵缩写不得跨所有字段做任意子串命中。注册表 Publisher 和未签名文件的 CompanyName 均可能被伪造，不能单独授权清理。

## 系统宿主排除

`msiexec.exe`、`rundll32.exe`、`regsvr32.exe`、`svchost.exe`、`explorer.exe`、`cmd.exe`、`powershell.exe`、`wscript.exe` 和 `cscript.exe` 只负责承载或启动目标，不能作为产品厂商证据。解析器应继续解析其目标 MSI、DLL、脚本或子命令；无法解析时保持未知。

## 行为判定

- `SystemComponent=1`、`NoRemove=1`、缺少卸载命令或控制面板不可见，只代表可见性状态，不能单独判定为流氓组件。
- 具体弹窗、广告、守护、自动恢复、浏览器策略强装等行为必须由独立的明确行为证据命中。
- 厂商身份达到“一项强证据或两项独立中证据”，且行为命中时，才按现有风险和清理规则处理。
- 厂商身份未知但存在明确独立异常行为时，只显示“未知第三方／仅提示”。
- 仅隐藏且身份未知、无独立异常行为时不显示，避免把正常软件内部组件列为可疑项。

## 各扫描入口改造

所有扫描器停止把字段传给 `RuleCatalog.IsKnownVendor(string)`。每个入口构造 `VendorEvidence`，调用统一解析器，再把 `VendorIdentityResult` 和独立行为结果传给 `NewFinding`。

- 右键、资源管理器、浏览器和文件关联：优先解析 command、COM Server、DisplayIcon 和宿主清单路径。
- 启动项、快捷方式、服务、计划任务和运行进程：优先解析真实可执行文件及其签名/版本信息。
- 卸载项：优先 Publisher、DisplayName、DisplayIcon、InstallLocation 和 MSI 元数据；ProductCode 与注册表键名禁止直接品牌匹配。

现有 `Evidence` 字符串继续用于报告和搜索，但不再作为识别算法输入。

## 错误处理与性能

- 文件不存在、拒绝访问、无签名、签名链离线、MSI 缓存缺失或元数据损坏时，身份补全返回部分结果，不中断扫描。
- 验签不启动目标文件，不执行卸载命令，不访问网络。
- 文件、签名、MSI 和安装目录归属结果均做扫描期缓存。
- 日志记录失败阶段和路径，不把失败自动视为可疑。

## 验收与回归

1. Corel GUID `{3D6825D1-5843-4585-B915-A9F234554C2C}` 不得识别成 2345，也不得仅因 `SystemComponent=1` 出现在结果中。
2. 为每个厂商加入 GUID、哈希、随机路径和参数偶然包含其短词的负向用例，全部不得命中。
3. `msiexec/rundll32/svchost` 等系统宿主的签名不得改变目标厂商。
4. Publisher、有效签名、CompanyName 或 MSI 元数据互相印证时，应正确显示厂商。
5. 两项强证据冲突时不得进入可清理列表。
6. 无签名但具有厂商特有组件名和安装目录归属的现有真实阳性仍应命中。
7. 现有十类扫描入口各保留至少一个阳性回归，并各增加弱词碰撞负向回归。
8. 编译、`--scan-smoke`、验证版 `--acceptance-test` 和真实本机扫描通过；逐项审查扫描结果中的厂商证据来源。
9. 同机扫描耗时不得因重复验签明显恶化；目标是不超过改造前基线的 30%。
